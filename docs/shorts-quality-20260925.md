## 범위와 정정

나눴다. 동일 대본은 현재 기본 분할에서 216자 한 구간이다. Studio의 C 프리셋도
기본 분할기를 쓰므로 이 대본에는 문맥 연결이 적용되지 않는다. 실험을 재현하려고

5. 화면의 “호흡/강조단위” 표현을 실제로 구현된 “생성 구간/질문·전환 등”으로 고쳤다.

## 추가 통제 비교: 텍스트 입력 방식

앞서 전체 대본 입력 방식을 평가한 것은 두 구간 연결 조건이었다. 그 결과를
단일 생성 쇼츠에도 일반화하지 않도록 `--suite input_mode` 비교를 추가했다.
설정은 기존 표현형 그대로 두고 `non_streaming_mode`만 False/True로 바꿨다.
이 옵션은 오디오 파일을 나누는 설정이 아니라 모델 내부의 텍스트 입력 방식이다.
설치된 코드와 [Qwen 공식 소스](https://github.com/QwenLM/Qwen3-TTS/blob/main/qwen_tts/inference/qwen3_tts_model.py)가 이를 구분한다.
두 조건 모두 실제 기본 분할기에서 한 구간이며, 모든 음성을 새로 생성했다.

| 대본 | 기존 입력: 길이 / CER | 전체 대본 입력: 길이 / CER |
| --- | --- | --- |
| story | 24.16초 / 0.00% | 24.63초 / 0.65% |
| explanation | 25.20초 / 2.70% | 24.61초 / 2.03% |
| conversation | 26.00초 / 2.04% | 24.16초 / 4.08% |

6개 모두 내용·파형 검사를 통과했지만, 전체 대본 입력이 모든 대본의 CER을 낮추지
않았다. 이 수치로 자연스러움 우열을 판정하지 않는다. 앞선 두 구간 실험에서의
시간 증가도 이번 단일 생성 실험에는 그대로 재현되지 않았다. 이번 실행의 생성·검사
시간은 기존 입력 약 106~116초, 전체 입력 약 96~98초였으며 첫 실행 준비/워밍업과
시스템 부하가 통제된 성능 벤치마크는 아니다.

결과: `data/comparisons/shorts-input-mode-20260925/{report.json,listen.html}`.
이 비교 페이지는 A/B 두 조건이고 앞의 4조건 페이지와 별개다. 기존 12개 비교의
파일·알파벳·재생 순서는 유지했다. 모든 추가 raw/final WAV 해시를 재검증했다.

### 실제 서비스 실행 검증

선택한 story를 `Service.create_external_tts_request` → 실제 `JobRunner` → Qwen 워커
→ CPU Whisper 검사 → 최종 WAV 결합 경로로 새로 생성했다. 검증용 DB·출력 폴더와
로컬 워커 포트만 분리했으며, 생산 DB의 엔진과 참조는 읽기만 했다. HTTP 인증과
외부 설정 무시 동작은 회귀 테스트로 확인했고, 이번 GPU 검증은 HTTP 계층 아래의
실제 서비스 실행 경로를 사용했다.

- 최종 24.63초, Seed 13 첫 시도 통과, CER 0.65%, 누락·반복 경고 없음.
