# 두 PC의 AI 에이전트 협업 규칙

2026-10-23 사용자 합의. VoiceBench와 insta_auto에 같은 규칙을 적용한다.

## 기본 방식

- 두 개발자는 서로 다른 PC에서 AI 에이전트를 사용하며, 모두 저장소 전체를 수정할 수 있다.
- 같은 저장소에서 여러 작업을 병행한다. 저장소 전체 또는 파일을 고정 담당자에게 독점 배정하지 않는다.
- 작업별 브랜치에서 개발하고 최신 원격 main을 통합·검사한 뒤 일반 push로 main에 반영한다. PR 생성이나 별도 PR 리뷰를 필수 절차로 두지 않는다.
- 이슈 생성·조회·갱신·완료 판단·종료는 AI가 담당한다. 개발자에게 이슈 수동 관리를 요구하지 않는다.

## 시작과 범위 확장

1. 원격 변경과 열린 이슈·관련 브랜치를 확인한다. 기존 이슈와 목적이 같으면 중복 생성하지 않고 기존 작업과 연결한다.
2. 새 작업이면 이슈를 생성한다. 목적, 담당 에이전트/세션 구분, 작업 브랜치, 기준 커밋, 예상 수정 범위와 완료 조건을 기록한다. 비밀정보와 PC별 개인 자료는 넣지 않는다.
3. 최신 origin/main을 기준으로 작업별 브랜치와 독립 작업 폴더를 사용한다. 기존 폴더의 미커밋 변경을 임의로 초기화·이동·커밋하거나 다른 작업에 섞지 않는다.
4. 예상 파일 목록은 정보이며 수정 허가의 상한이 아니다. 작업 중 파일·기능 범위가 늘어나면 이슈를 갱신하고 다른 진행 작업과의 겹침을 확인한다.
5. 같은 파일의 독립적인 변경은 병행할 수 있다. 같은 함수의 의미, API, DB 구조, 설정 계약이 충돌하면 관련 이슈에 근거와 조정안을 기록하고 공통 변경을 조율한다. 독립적인 나머지 작업은 계속한다.
6. 다른 PC의 로컬 변경은 직접 보이지 않으므로 논리적인 작업 단위마다 브랜치와 진행 범위를 공유한다. 이슈나 Git 병합 성공을 파일 잠금 또는 기능 정상의 증거로 보지 않는다.

## 없어지는 내용은 명시적으로 확인

- 기존 기능·동작·공개 API·설정·DB 필드·자료·문서 규칙이나 상대 작업의 실질적인 내용이 없어지거나 축소되면, 적용 전에 무엇이 없어지는지, 이유, 영향, 대안을 사용자에게 설명하고 명시적 동의를 받는다.
- 사용자 또는 해당 작업에서 이미 동일한 대상·범위의 제거를 명시적으로 승인했다면 그 근거를 기록하며 중복 승인을 요구하지 않는다.
- diff의 삭제 줄을 검토하되 줄 수만으로 판단하지 않는다. 같은 동작을 유지하는 구현 교체와 기능·내용의 실제 소실을 구분하고, 판단이 불확실하면 확인한다.
- 병합 충돌을 해결하려고 상대 코드를 통째로 버리거나 ours/theirs를 일괄 선택하지 않는다. 양쪽 의도를 보존하며, 의미 있는 제거가 필요하면 위 확인 절차를 따른다.
- 자동 push 권한은 내용 제거의 포괄 승인이나 데이터 삭제·운영 중지 해제·게시·배포 승인이 아니다.

## 완료와 자동 push

사용자는 2026-10-23 추가 답변으로 **AI가 구현·검증 완료를 판단하면 별도 요청 없이 자동 push**하도록 확정했다. 이는 앞서 논의한 매번 사용자에게 작업 완료를 묻는 절차를 대체한다. 완료 조건 충족과 필요한 검사 통과를 AI가 판단하며, 작업 완료 여부나 push 승인을 다시 묻지 않는다. 의미 있는 내용 제거 동의, 불명확한 요구사항 또는 실제로 필요한 사용자 확인은 별도로 유지한다.

1. 현재 작업의 변경만 묶고 관련 검사를 수행한다. 작업과 무관한 미커밋 파일·개인 음성·세션·인증정보·모델·로컬 DB·생성 미디어·복구 백업을 포함하지 않는다.
2. push 직전에 origin/main을 다시 fetch하여 작업 브랜치에 병합한다. 새 코드와 기존 코드의 연결, 삭제/축소 내용 및 의미 충돌을 확인하고 영향받는 검사를 수행한다.
3. 일반 fast-forward push로 작업 브랜치의 HEAD를 원격 main에 반영한다. main에 대한 강제 push, 강제 덮어쓰기, 실패한 검사 무시는 금지한다.
4. 상대의 선행 push로 거절되면 원격 main을 다시 받아 변경을 통합하고 영향받는 검사를 다시 수행한다. 같은 실패를 진전 없이 무한 반복하지 않는다.
5. 성공 후 원격 main이 내 완료 커밋을 포함하는지 확인한다. 다른 작업이 바로 추가될 수 있으므로 원격 HEAD가 내 커밋과 같아야 한다고 강제하지 않는다.
6. 이슈에 변경 요약·검사 결과·반영 커밋·남은 제한을 기록하고 요청한 완료 조건이 충족됐을 때 닫는다. 실패·중단·사용자 답변 대기는 열린 상태로 이유를 남긴다.
7. 코드의 원격 반영과 운영 적용은 별개다. 실제 서비스 적용이 완료 조건이면 그 확인 전에는 전체 완료로 보고하지 않는다.

## 기존 운영 보호

이 규칙으로 제작·수집·예약·모델·서버·휴대폰 제어·실제 게시를 재개하지 않는다. 기존 사용자 중지, 서비스 간 API 경계, 개인 자료 보존 및 프로젝트별 품질 규칙을 유지한다.

이 사용자 합의는 이전의 일반적인 "매번 커밋/push 지시를 기다린다"는 규칙보다 우선한다. 기존 작업 이력의 "미커밋/미푸시"는 그 시점의 상태 기록으로 보존한다.
